# Synthetic 4.0 eval corpora

Four opt-in corpora, generated from seed `40891` (generators in `corpus/synthetic-*.ts`, SHA-256 data fingerprint in each spec). Every document is fictional. No account, live brain or Cloudflare API is used: the loader uses the production index write path over local D1, exact-cosine Vectorize and the pinned local embedding model. Default runs (`npm run eval:recall -- --variant baseline`) still select `core-1k` and never include these.

## Reproduce

Install with `npm ci`. For each corpus ID in `temporal noise injection`:

```sh
npm run eval:recall -- prepare --variant baseline --corpus ID
npm run eval:recall -- --variant baseline --corpus ID
```

For `standing`, use `--variant no-rerank` and add `--max-neurons 6000` to `prepare` (the byte-count estimate is about 4,100 production-equivalent neurons; nothing is billed, embeddings are local). `prepare` records content-addressed embeddings in `.eval-cache/replay/<corpus>.*.jsonl`; the second command is fully offline. Caches are not committed, as for public corpora: only the core cache is committed by repo convention, and these corpora never read or write it. Add `--json PATH` for a machine-readable report. `temporal` also works with `--compare no-rerank,baseline --target knowledge-update` (Track 2's current-state gate; `temporal-during` is report-only, not a target, see below); `noise` with `--target noise` (a Track 3 regression guard with a proven sub-margin gain, see below); the gate's cost check stays inconclusive on the sqlite backend, as everywhere.

| Corpus / category | Docs | Queries | Clusters | Role |
| --- | ---: | ---: | ---: | --- |
| `temporal`, category `knowledge-update` | 615 | 120 | 120 | GATE for Track 2's current-state path |
| `temporal`, category `temporal-during` | 615 | 100 | 100 | REPORT-ONLY: not yet a gate; see below |
| `temporal`, category `temporal` (`prefiltered` + `phrase-dated`) | 615 | 240 | 240 | REPORT-ONLY. Do not target: see below |
| `temporal`, `control-not-asof` | 615 | 30 | 30 | REPORT-ONLY, part of the `temporal` category; fixed by T-0089.2.5, see below |

| `standing` | 2,517 | 1,500 | 1,170 | GATE for choosing Track 7's threshold, with caveats below |

A gate needs at least 200 queries and 30 clusters and the corpus must contain the failure it is meant to catch. Meeting the query and cluster floor is not enough: a corpus is a gate only where a wrong change is shown to fail it and a right change is shown to pass it. `temporal-during` meets the floor (100 queries, 100 clusters, MDE 0.031) but not the second condition: round 4 found several changes with no as-of logic at all still pass it on the recorded baseline (see below), so it stays report-only alongside `temporal`, which round 3 already excluded for a related reason. `standing` is a threshold-selection gate, not a paired before/after gate: it has no baseline/candidate comparison, only a dev-chosen operating point scored on held-out data.

## temporal (GATE for `knowledge-update` only; `temporal-during` and `temporal`, including `control-not-asof`, are report-only)

What it measures. 120 timelines, each with a distinct pseudo-word subject ("Velmora studio lease", no numbered siblings), in four shapes: `update` (35), `retro` (35, backdated notes and a recap written after the fact), `retracted` (30, a fact later withdrawn by a correction), `edited` (20, a document edited after the as-of date). Each timeline gets a current-state question (category `knowledge-update`, gold = the fact valid now). Its past questions split across three categories:

- `temporal` (report-only, 270 queries): `prefiltered` ("Where was X in April?" with a per-query `asOf`; the runner passes `before: asOf + 1`, so the newer fact is excluded and this only tests ranking among older documents), `phrase-dated` ("as of April 15, 2026", not pre-filtered, so the phrase parser is exercised), and `control-not-asof` (see below). **Do not target this category.** Before T-0089.2.5, the shipped parser turned a date-shaped phrase into a created-on-that-day filter that returned nothing, so `phrase-dated`'s baseline of 0 looked identical to a parser deleted entirely (round 3), and `control-not-asof` scored 0/0 outright (round 2). T-0089.2.5 fixed both misreadings (see below); `phrase-dated` is still not a target, because in 115 of 120 queries tense wording alone ("was" vs "is now") already puts the old fact above the new one without any date parsing, so this subset still cannot distinguish a correct as-of implementation (which does not exist yet, see the T-0089.2.5 section below) from no implementation at all.
- `temporal-during` (**report-only, not yet a gate**, 100 queries in 100 clusters): `phrase-vague`, `backdated-past` and `retracted-past` ("during April / July", no pre-filter). `expectedAsOf` records the date for the oracle. See "Not yet a gate" below for why.
- `control-not-asof` (30 questions naming a place such as "the Aug 8 ... Cafe"; correct behaviour is ordinary retrieval, unaffected by a date parser). Fixed by T-0089.2.5 (see below); part of the ordinary `temporal` category, no tag.

### `temporal-during`: not yet a gate

Round 4 re-scored the **recorded baseline** (a real embedding run, not an invented fixture) through `evaluateGate` and found two problems, both plainly stated here rather than argued around:

**Reason 1: in every "during" subset, the gold is never the newest document of its timeline.** `phrase-vague`'s gold (`old`) is older than `new`; `backdated-past`'s gold (`new`) is older than the later `recap`; `retracted-past`'s gold (`old`) is older than `fix`, which in fact outranks it in all 30 baseline queries. Because of that one-sided structure, several changes with no as-of understanding at all still pass `--target temporal-during`, and one genuinely damaging change slips through a subset unseen because the gate judges only the whole category:

| Candidate (re-scored from the recorded baseline) | Verdict | Category MRR delta | phrase-vague / backdated-past / retracted-past MRR |
| --- | --- | ---: | --- |
| Baseline | -- | -- | 0.498 / 0.514 / 0.339 |
| Supersession oracle (correct: drop what the declared validity excludes) | PASS | +0.539 | 0.986 / 1.000 / 1.000 |
| Demote the newest document of the timeline | **PASS** | +0.382 | 0.952 / 1.000 / 0.517 |
| Demote "Correction" / "Looking back" documents | **PASS** | +0.224 | 0.500 / 1.000 / 0.517 |
| Boost documents containing " was " | **PASS** | +0.141 | 0.986 / **0.291** / 0.500 |
| Supersession, but the cancelled move ("bad") ranked first | **PASS** | +0.389 | 0.986 / 1.000 / 0.500 |
| Boost any document carrying an explicit date | no win (below margin)\* | +0.040\* | 0.498 / 0.514 / 0.472\* |
| As-of on `created_at` only, no upper bound | FAIL (regression) | -- | 1.000 / 0.000 / 0.517 |
| As-of on `created_at`, respects `valid_until`, ignores backdating | FAIL (regression) | -- | 1.000 / 0.000 / 1.000 |
| Belief-time as-of (show `bad`, hide `old`) | FAIL (regression) | -- | 0.498 / 1.000 / 0.000 |
| Keep only the newest document of the timeline | FAIL (regression) | -- | 0 / 0 / 0 |
| Supersession, drops the whole retracted timeline | FAIL (regression) | -- | -- |

The "boost documents containing 'was'" row passes at the category level while `backdated-past` alone collapses from 0.514 to 0.291, the exact failure that subset exists to catch: **the gate as built cannot see a subset-level loss inside a category-level pass.** This table is the builder's own recomputation against the corpus's real gold, validity data and the recorded baseline report through the real `evaluateGate` (not `temporal-gate.test.ts`'s hand-built fixture, which proves gate mechanics only, not corpus validity; see that file's header). \* The "boost any document carrying an explicit date" row is close to but not an exact replay of round 4's probe (which reported +0.053, PASS): the exact heuristic wasn't fully specified, and this builder's best-effort reimplementation lands just under the improvement margin. The direction is the same either way and does not change the conclusion.

**Reason 2: the `retracted-past` gold conflicts with the approved Track 2 plan on a decision this corpus cannot make.** The plan (02-time-aware-truth.md, D2.1/D2.2 and the as-of section) has supersession set `old.valid_until` when `bad` arrives, and an as-of query then shows the later-deprecated memory, labelled "later retracted" (belief-time). An implementation that follows the plan therefore returns `bad`, which is exactly the "belief-time as-of" row above, and that row **fails** the gate under the corpus's current gold. The corpus's own validity data (`old` open-ended, `bad` empty) is valid-time semantics the plan does not specify, so the conflict is real, not a bug in either side. This is a product decision for Rahil, not one this corpus should make on his behalf:
- **Option 1, belief-time (follows the plan as read today):** gold becomes `[bad]`, with `old` valid February to July and `bad` valid July to August.
- **Option 2, actually-true (the plan gains a rule):** "a retraction restores the superseded fact," and gold becomes `[old, fix]`.
- Until the decision is made, `retracted-past` is part of the report-only `temporal-during` category along with the other two "during" subsets; the remaining `phrase-vague` and `backdated-past` (70 queries, 70 clusters) still clear the gate's power floors on their own if a narrower gate is wanted sooner.

**What a future `temporal-during` gate needs**, once these are resolved:
1. "During" questions whose gold **is** the newest valid document of its timeline (for example, an `update` timeline asked "during August", after the move), so that both recency and anti-recency shortcuts fail somewhere and only real validity reasoning passes everywhere.
2. Per-subset regression protection, so a subset collapsing (like `backdated-past` under the "was"-boosting row above) cannot hide behind a category-level pass; splitting each "during" subset into its own category, as this round split `temporal-during` out of `temporal`, is the mechanism this repo already uses for that.
3. Rahil's retraction-semantics decision (Option 1 or Option 2 above), with the corpus's validity data and gold brought into agreement with whichever is chosen.

None of this is built in this round. Designing the Track 2 as-of gate belongs with the Track 2 spec, once the semantics decision is made.

T-0089.2.5: `control-not-asof` was excluded, then fixed (history). Before this fix, the shipped parser misread these month-day names as dates, so the baseline itself scored 0/0. A delta-from-baseline rule compares a candidate against that same 0, so a worse candidate parser could not show as a regression: both scored 0, with nothing left to fall to. Concretely, a parser that read every month-day-shaped string as an as-of date got 40% of these controls right (0.60 MRR) against a correct parser's 1.00, yet a delta-based rule still called 0.60 an improvement over the 0 baseline (asserted in `temporal-gate.test.ts`, kept as a fixture: the "misreading" candidate passes `--target-gaps temporal-month-day-controls` exactly as the "correct" one does). **The mechanical target-gaps rule alone cannot tell those two apart; `gate.ts` was not changed to try.** Instead, T-0089.2.5 (filed on the board, parent T-0089.2) landed first in Track 2, fixing `src/text/temporal.ts` so a month-day match followed by a proper noun (a name, not a date) and an "as of" phrase are no longer read as a created-on-that-day filter. Both acceptance parts, mechanical and manual, held before the tag was removed:
1. `npm run eval:recall -- --compare no-rerank,baseline --corpus temporal --target-gaps temporal-month-day-controls` reports a passing `improvement` rule (the delta on this particular pair is 0, since both compared variants share the same, already-fixed code; the printed rule still reports pass because the pair's own overall reranking gain clears the margin, and no regression rule fires); and
2. the printed `known gaps` row for `gap:temporal-month-day-controls` reached **MRR@10 >= 0.95** (it reached 1.000, printed as "acceptance floor MRR@10 0.95 (T-0089.2.5): met"), confirmed by comparing a real embedding run of the pre-fix parser (MRR@10 0.000 on this row) against the same run of the post-fix parser (MRR@10 1.000), both `--variant baseline --corpus temporal`.

With both parts held, the `gap:temporal-month-day-controls` tag was removed from the 30 control queries in `corpus/synthetic-temporal.ts`; they now rejoin the ordinary `temporal` category's regression rule (report-only, as above) and protect every later temporal change from the same class of misreading. `MONTH_DAY_CONTROL_GAP_TAG` and `MONTH_DAY_CONTROL_ACCEPTANCE_MRR` remain in `corpus/synthetic-temporal.ts`, no longer applied to any query, kept only as pinned fixture values for `temporal-gate.test.ts`'s and `synthetic-acceptance.test.ts`'s gate-mechanics tests and for this history.

Data model (`corpus/types.ts`). `CorpusEntry` gains `updatedAt`, `validFrom`, `validUntil`, `retractedAt`, `priorVersions`; supersession is a `supersedes` edge (newer to older). The loader writes `updated_at` and the edges today. `applySupportedTemporalMetadata` (`corpus/loader.ts`) writes `valid_from`/`valid_until` only when the entries table has those columns (none yet), and `loadCorpus` takes a `temporalMetadata` writer as the extension point for Track 2's write path. Queries gain `expectedAsOf`. Documents are dated at noon UTC so the local-time date parser gives the same answer in every timezone from UTC-11 to UTC+11.

`retracted-past` gold, currently. "Where was X during July?" after a move to B was announced and later corrected as never having happened. The gold today is `old` (A) only, grade 2, the actually-true reading; this is one candidate answer, not a settled one, per Reason 2 above. The validity data agrees with the current label: `bad` declares an empty window (`validUntil` equal to `validFrom`, half-open, never valid), meaning it was never actually true, while `retractedAt` still separately records when the correction was learned. `synthetic-report.ts` prints how often the cancelled move still surfaces in the top 10 (today, 30 of 30 `retracted-past` queries) as a diagnostic, not as something a change is judged on. An earlier draft graded the announced move `bad` (B) as partially relevant (1) alongside `old`; round 3 found this let a system that ranks the cancelled move first score exactly as well as one that ranks the actually-true answer first, since `recallAtK` and `mrrAtK` both ignore grade and stop at the first gold id they see.

Oracle (`temporal-oracle.ts`, printed in the report). From the recorded rankings alone it simulates (a) supersession applied: drop documents whose declared validity excludes the question date; (b) recency only: reorder by creation time, which the backdated recap defeats. Its query and cluster counts match the headline (a round-3 finding was that they previously disagreed when the known-gap controls were excluded from one but not the other, "temporal n=370" against the headline's 340; the exclusion, and the mismatch it could cause, is now moot, since T-0089.2.5 removed the gap tag and `control-not-asof` counts in both). This is an upper bound on what dropping invalid documents can do to today's ranking under the corpus's own (currently actually-true) validity data, not a prediction of Track 2's contradiction detector, and not independent of the Reason 2 decision above: the loader writes validity exactly as the corpus declares it, so the ceiling assumes both perfect contradiction detection at capture and the actually-true reading of retraction. Baseline current-state MRR@10 is 0.702; supersession applied 0.809 (the ceiling given what the pool returns); a plain recency reorder falls to 0.212. On `temporal-during`, supersession applied 0.456 to 0.995 MRR; recency-only falls to 0.178. Per subset: `backdated-past` 0.514 to 1.000 (recency falls well below baseline: the exact case round 4's candidate table above shows a category-level pass can hide); `retracted-past` 0.339 to 1.000; `phrase-vague` 0.498 to 0.986. `control-not-asof` (already fixed, so supersession has nothing to gain): 1.000 baseline falls to 0.667 under a plain recency reorder, since these controls have no timeline to defend against reordering; not gated, printed for completeness.

Baseline, after T-0089.2.5 (recall@10 / MRR@10; no known gaps remain in this corpus): overall 0.898 / 0.639 (n=490); `knowledge-update` 0.958 / 0.702 (n=120); `temporal-during` 1.000 / 0.456 (n=100); `temporal` 0.833 / 0.679 (n=270). Subsets: current 0.958 / 0.702, prefiltered 0.917 / 0.736, phrase-dated 0.708 / 0.542 (report-only, no longer 0/0), phrase-vague 1.000 / 0.498, backdated-past 1.000 / 0.514, retracted-past 1.000 / 0.339, control-not-asof 1.000 / 1.000 (fixed, no longer a known gap). Before the fix (recorded for history): overall 0.707 / 0.474 (n=460, known-gap `control-not-asof` excluded from the headline); `temporal` 0.458 / 0.368 (n=240); phrase-dated 0 / 0; control-not-asof 0 / 0 (known-gap; all queries including it, n=490: recall@10 0.663 / MRR@10 0.445).

Power. Unpaired MDE for MRR@10 at 80% power, two-sided 95% (2.8 x bootstrap SE over clusters): 0.068 overall for the whole corpus (n=490, no known gaps left to exclude), 0.031 within `temporal-during` alone (n=100). Both are comfortably under the 0.05 target margin a gate's target path would use, which is exactly why `temporal-during` is held back on validity grounds (above) rather than power: the corpus can already resolve effects at this size.

Cannot measure. Id-level gold cannot check that an as-of view shows the earlier version's text; `edited` timelines declare `priorVersions` for that future path and today only test retrieval. Contradiction detection at capture is unmeasured (see the oracle caveat above), and the loader writes with `storeEntry`, not `captureEntry`, so the LLM check does not run here.

## noise (REGRESSION GUARD for Track 3, with a proven but sub-margin gain; not yet a pass-the-margin gate)

T-0089.3.5 rebuilds this corpus after a round-2 review found the original had no headroom for the change Track 3 exists to make: in the synonym probes, when the gold missed the top 3 the slots were filled by other genuine notes (47 of 54 cases), not by mail, because the corpus's own filler notes reused the probes' trigger words ("choosing", "sign in", "account") and, being short and keyword-dense, out-competed the long, footer-diluted mail for exactly the queries meant to test the mail attractor. Fixed here by giving filler notes a disjoint vocabulary, adding a dedicated near-duplicate-crowding scenario, and a T-0089.3.5 director addition: `codex-session` and `cursor-session`, two automatic-transcript clients Track 3 is adding (classified `TRANSCRIPT_SOURCES`, not yet in `src/constants.ts` as of v4/t3-r 60b84f78), get the identical treatment as email (a shared wrapper, near-duplicate chore excerpts, crowding, and controls). Because every core-1k document has source `api` (direct), core-1k cannot move under a source-class weight at all; this corpus is Track 3's only real gate for that change.

**Round 2 correction (Codex review, this round).** The first version of this round's gate proof used a hand-rolled reranking oracle in `noise-oracle.ts` that took the query's own `gold` field and exempted gold from being collapsed or demoted. A candidate that can see the answer key is an oracle, not a reranker, and the numbers it produced (an apparent +0.0223 MRR@10 gain clearing the gate's margin) proved nothing about production behavior. Fixed by importing lane R's actual, unmodified functions (`src/recall/source-trust.ts`'s `collapseNearDuplicates` and `applyOccupancyCap`, v4/t3-r 60b84f78, merged into this branch) and building every candidate from a `CorpusEntry` alone (`id`, `content`, `source`, `tags`, `createdAt`): there is no parameter gold could arrive on. `noise-gate.test.ts` also proves this at runtime, not just by type: every test-half query is reranked through a `Proxy` that throws if anything ever reads `.gold`, and the whole suite passes with zero throws.

One consequence of using the real functions: production's `collapseNearDuplicates` collapses **mirror rows only**, never transcript (its own `sourceClass(...) !== "mirror"` guard). Chore-transcript near-duplicates are therefore never collapsed by production today, only capped; the `transcript-crowding` gain below is smaller than the round-2 (invalid) proof reported for that reason, not because the corpus regressed. `sourceWeight` itself is a multiplier applied to a raw fused score before ranking (`src/recall/math.ts`); a recorded report carries only the final rank order, no scores, so it cannot be replayed from this data at all and is not attempted here. This proof therefore covers collapse and the occupancy cap only.

Reproduces the Aug 16 mechanism twice over: 6 mail senders plus 4 more with their own templates, all ending in one identical long footer ("Thanks for choosing us. Sign in to your account ...", repeated as real mail repeats it), 90 near-identical direct-deposit notices differing only in amount and reference; and 60 near-identical chore transcripts ("Ran npm test for CI run ..., group G01 ...") sharing a wrapper open/close line per client. Filler notes use a vocabulary disjoint from both the footer/wrapper words and every query template, so they cannot win a probe or control by accidental overlap.

Queries (510, one query per cluster). Mail: `probe-footer-words` (40) and `probe-footer-synonym` (90, 3 phrasings per topic): "choosing a name for the new feature", "who did I thank for ...", share only footer words with the mail; the answer is a genuine note, in the synonym tier written with no query words. `mail-crowding` (54, 3 phrasings per topic): "What did I decide about how my direct deposit is split between two bank accounts?", the query (not the note) carries "direct deposit" / "payroll" words that pull in the 90 near-duplicates. `recurring` (40): "Show the direct deposits from payroll batch PB07" has three golds among 90 near-identical notices, plus amount lookups. `email-control` (60): flights, prescriptions, bills, half phrased "in my email ..." / "according to my email", half transactional ("what is the confirmation code for the flight booking") with no source word at all. `note-same-topic` (40): a genuine decision note on a topic that also has mail. Transcript, the same shape: `transcript-probe` (12), `transcript-crowding` (54, 3 phrasings per topic), `transcript-recurring` (30), `transcript-control` (30, half phrased "in my cursor/codex session ..."), `note-same-topic-transcript` (60, 3 phrasings per topic). Source alone never separates gold: mail, transcript and genuine notes are all gold, on the same topics.

Dev/test split. Track 3 tunes its source weights, the occupancy cap and the near-duplicate collapse against this corpus, so the gate that judges the tuned result is scored on a held-out half tuning never saw, the same way `standing` withholds a split (tag `split:dev` / `split:test`, hashed per query id so a whole subset cannot land on one side by chance of generation order; confirmed live that a sequential counter can do exactly that). Skewed so the test half alone clears the gate's power floor: 351 queries, 351 clusters (dev: 159).

Baseline, full corpus (recall@5 / recall@10 / MRR@10, n=510): overall 0.800 / 0.833 / 0.737. Subsets: probe-footer-words 1.000 / 1.000 / 0.988; probe-footer-synonym 0.433 / 0.556 / 0.261; mail-crowding 0.611 / 0.630 / 0.568; recurring 1.000 / 1.000 / 1.000; email-control 1.000 / 1.000 / 0.992; note-same-topic 1.000 / 1.000 / 1.000; transcript-probe 1.000 / 1.000 / 1.000; transcript-crowding 0.500 / 0.593 / 0.427; transcript-recurring 1.000 / 1.000 / 1.000; transcript-control 0.967 / 0.967 / 0.867; note-same-topic-transcript 0.967 / 0.967 / 0.861. Email share of the top 3: 0.125 (literal probes), 0.081 (synonym probes); gold note in the top 3 for 40/40 (literal) and 34/90 (synonym). Email-correct queries with no email in the top 5: 0. Unpaired MDE for MRR@10: 0.050.

### Gate proof, on the recorded baseline, production functions only (`test/eval/noise-gate.test.ts`, `corpus/noise-baseline.recorded.json`)

Per the round-4 lesson on `temporal-during` (above) and this round's own Codex-review correction: a gate label needs the real `evaluateGate` run on candidates re-ranked from a RECORDED baseline by PRODUCTION code, never invented rankings and never a candidate that can see gold. `noise-oracle.ts`'s `productionRerank` calls `collapseNearDuplicates` then `applyOccupancyCap` (production's own order, `src/recall/search.ts`) with D3.1's approved tuning (mirror 0.85 / transcript 0.9 / system 0.95 demotion is not simulated, see above; `MIRROR_MAX_SHARE` 0.4) and the cap's transactional lift turned on (`includeTransactional: true`, since half of `email-control` is transactional wording rather than a source word; this is itself an open tuning question, grid axis L in the Track 3 spec, that this eval surfaces rather than settles). Test half only, n=351, 351 clusters, bootstrap 1000-2000 iterations:

| Candidate | Verdict (regression / improvement) | Overall MRR@10 delta | email-control / transcript-control MRR@10 delta |
| --- | --- | ---: | --- |
| Baseline | -- | -- (0.749) | -- |
| Production collapse + occupancy cap (transactional lift on) | regression PASS, improvement **FAIL (sub-margin, not a loss)** | +0.0057 [0.0018, 0.0106] | 0.0000 / 0.0000 |
| Blanket demotion of every mirror/transcript row, no source-word lift | regression **FAIL** | -0.0419 [-0.0708, -0.0158] | -0.2066 / -0.4647 |
| Dropping every mirror/transcript row outright | regression **FAIL** | -0.2618 [-0.3132, -0.2111] | -0.9872 / -0.8571 |
| Pure recency (source class and relevance both ignored) | regression **FAIL** | -0.5516 [-0.5892, -0.5131] | -0.7939 / -0.6722 |

**Honest reading of the correct candidate.** The overall MRR@10 delta's bootstrap CI excludes zero (0.0018 to 0.0106): there is a real, non-zero, statistically proven effect, not noise. But its mean (0.0057) is well under the gate's 0.02 improvement margin, so `evaluateGate`'s improvement rule reads FAIL, correctly: the study is well-powered enough to have detected a 0.02+ effect had one existed (this is not the "underpowered" case gate.ts also has a message for), it measured a smaller real one instead. The gain concentrates in two subsets: `probe-footer-synonym` +0.0276 [0.0079, 0.0518] and `transcript-crowding` +0.0069 [0.0000, 0.0208]; `mail-crowding` and `note-same-topic-transcript` show exactly zero movement. All three wrong candidates fail the regression rule outright and specifically destroy the "wants the mail/transcript" controls (down to near zero for drop-non-direct), which is exactly the over-demotion failure mode the occupancy cap and its source-word lift exist to avoid, and exactly what a corpus that could only measure no-harm (the pre-T-0089.3.5 round) could not show either way.

Cannot measure. `mail-crowding` and `note-same-topic-transcript` show no recovery: `mail-crowding`'s gold is either already ranked first (nothing to fix) or pushed past what a top-10 rerank can see (a recorded report carries only the top 10; nothing below that rank is available to a post-hoc re-ranking simulation); `note-same-topic-transcript`'s queries are answered by a direct note competing against transcript rows that, being transcript-class, are never collapsed by production and rarely cross the occupancy cap's threshold alone. `sourceWeight`'s own contribution is entirely unmeasured here (no scores in a recorded report, above); a live or `--d1 workerd` run with the real scoring pipeline would be needed to see whether the mild per-class multiplier closes the remaining gap on these two subsets and pushes the overall gain past the margin. The live brain's original 7-of-10 email top 10 (the Aug 16 diagnosis) was not reproduced at this size against a fictional mailbox; do not read this corpus's email/transcript share as the production rate.

## injection (REPORT-ONLY)

80 targeted subjects, each with a genuine note (gold), one planted email, and two benign emails on the same topic, inside 5,000 documents (plants 1.6%). Four plant styles, 20 each, tagged `plant-<style>`: `command` ("Ignore previous instructions ..."), `role` ("SYSTEM NOTICE to the assistant ..."), `factual` (poisoning with no command words: "the plan was cancelled"), `impersonation` ("Note to self: I changed my mind"). Metric: share of top-5 slots taken by planted documents for the targeted queries.

Baseline: planted top-5 share 0.397 (159/400 slots), 0.39 to 0.40 for every style; gold recall@5 1.000, MRR@10 0.268 (plants outrank the note). Own plant is rank 1 in 12/20 command, 11/20 role, 18/20 factual, 17/20 impersonation queries. MDE at 80% power, slot-level binomial: 0.069. Because the plants mimic the notes' subject, occupancy is high in every style; the factual style, which a command-word filter cannot catch, ranks first most often.

Cannot measure. Retrieval occupancy is not compliance: whether a model obeys a planted email needs a model and belongs to Track 5. Plants for other subjects share templates and appear in each other's results: 79 of 80 queries hold exactly two plants in their top 5, the targeted one plus one sibling-subject plant, so the occupancy metric is close to structural rather than a graded signal, and the effective independent sample is the 80 subjects, not 400 slots. ## standing (GATE for choosing Track 7's threshold, with caveats)

30 standing memories ("When booking a flight, check the shared calendar for conflicts first.") placed inside the core-1k documents (2,517 documents in all), all distinct situations so no memory has a sibling variant. Queries (1,500): 150 positives (5 phrasings per memory, gold = the memory); 120 `standing:overlap` negatives (different subject reusing the memory's key word, must not fire); 90 `standing:intent` (same subject, different intent such as "summarize the history of ...": the label is a product decision, reported apart and excluded from precision); 1,140 `standing:unrelated` (ordinary core-1k questions), so positives are 10% of traffic. Half the memories and half of the unrelated queries form a held-out `split:test`.

Method. Recall's embedding of each query is captured (`distilled`, what recall really sent to the model) and the raw query text is embedded too (`raw`). Each is compared by exact cosine with every standing memory's vector; at most two memories fire above a threshold, grid 0.30 to 0.90 by 0.05. Precision = TP / (TP + FP) over positives, overlap and unrelated queries; recall = TP / (TP + FN). The threshold is chosen on the dev split only (highest recall with precision at least 0.9, else best F1) and reported on the test split with 95% Wilson intervals. Product wiring is out of scope; Track 7 decides which input it uses.

Baseline. Distilled: chosen 0.75, held-out precision 1.000 [0.566, 1.000], recall 0.067 [0.029, 0.147]. Raw: chosen 0.70, held-out precision 1.000 [0.901, 1.000], recall 0.467 [0.358, 0.578]. Across all splits at 0.70: distilled precision 0.906 / recall 0.320, raw 0.988 / 0.540; at 0.65 raw is 0.834 / 0.840. The raw input clears the Track 7 goal (precision at least 0.9, recall at least 0.7) nowhere on this grid, but is far closer than the distilled one, whose dropped words cost most of the recall. Same-subject-other-intent queries fire in 15/90 (raw) and 23/90 (distilled) at 0.70 and in 66-73/90 at 0.60.

Gate caveats. Three open items keep this a gate "with caveats" rather than an unconditional one: (1) same-subject-other-intent fires (`standing:intent`) are excluded from precision because whether they should count is Rahil's product decision, not yet made; a decision to count them would move the chosen threshold. (2) The Wilson intervals are computed per query, not per memory, but true positives cluster by memory (raw's 0.70 test-split precision comes from 15 held-out memories, not 75 independent trials), so the printed intervals are narrower than the real uncertainty; treat them as optimistic, the same direction as injection's MDE. (3) The precision curve sits at a cliff: raw goes from 0.834 at 0.65 to 0.988 at 0.70, so the chosen operating point is sensitive to small changes in the embedding or the grid spacing (0.05 wide), and a production threshold should be re-validated rather than copied from this grid directly.

Cannot measure. The memories are hand-written and templated in phrasing (5 positive templates), so intervals reflect the 15 held-out memories, not the space of real instructions; unrelated traffic is core-1k question text, not real chat, and the 10% positive prevalence is asserted by construction, not measured from production.
